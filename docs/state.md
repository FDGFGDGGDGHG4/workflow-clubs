# Уровень 3: состояние и взаимодействия

## Владение состоянием

| Вид | Данные | Единственный источник |
| --- | --- | --- |
| URL state | Поиск, статус, приоритет, клиент, исполнитель, категория, сортировка, страница, размер страницы | query-параметры маршрута, нормализованные в useRequests |
| Local state | Открытая форма смены статуса, выбранный новый статус, текст комментария, отправка и ошибка формы | ref в карточке заявки |
| Server state | Заявки и их версии, справочники, комментарии и история | API; клиентский кеш useFetch/useNuxtData |
| App state | Плотность списка | Pinia preferences; localStorage служит сохранением настройки |
| App state | Последнее отменяемое действие, уведомление, блокировка параллельных изменений | Pinia requestUi, только в текущем сеансе |

Заявки не копируются в глобальный store. Компоненты по-прежнему получают данные через useRequests/useRequestLookups и props RequestList. Мутации вынесены в useRequestMutations: они обновляют те же записи кеша, которые читают список, обзор и карточка. Плотность применяется одной настройкой к любому RequestList.

## Изменения

PATCH /api/requests/:id принимает version и ровно одно поле: priority, status или assigneeId (null снимает назначение). При несовпадении версии сервер отвечает 409. Успех возвращает заявку с увеличенной версией и сохраняет историю. Приоритет меняется в кеше до завершения запроса; ошибка восстанавливает прежнее значение. Для 409 и 500 предусмотрены отдельные сообщения. После успешной записи кеши списков обновляются с учётом фильтров и количества записей.

Undo хранит предыдущий статус или приоритет и версию успешного изменения. Отмена — новый PATCH, поэтому состояние восстанавливается и на сервере. Ошибка Undo сохраняет возможность повтора. Изменение исполнителя не стирает последнюю отменяемую операцию. Новое успешное изменение статуса/приоритета заменяет предыдущую Undo-операцию.

POST /api/requests/:id/comments принимает text (1–4000 символов) и operationId. Один operationId не создаёт два комментария: после потери ответа повторная отправка безопасна. При ошибке текст остаётся в форме. GET /api/requests/:id/activity возвращает комментарии и историю.

## Хранение

Данные сохраняются через Nitro storage в .data/workflow (папка исключена из Git). Они переживают обновление страницы и перезапуск процесса. Локальный файловый адаптер предназначен для одного Node-процесса; для нескольких экземпляров приложения нужна общая БД с атомарной проверкой версии. Стартовые данные и терминология детских кружков сохранены из уровня 2.

## Проверка вручную

1. Открыть /requests, изменить приоритет строки: новое значение видно сразу. Нажать «Отменить изменение», затем обновить страницу.
2. Открыть карточку, назначить исполнителя, сменить статус, добавить комментарий. Перезагрузить страницу и проверить сохранение.
3. В двух вкладках открыть одну заявку. Изменить её в первой, затем без обновления изменить во второй: получить 409, прежнее значение и сообщение о конфликте. Нажать «Обновить заявку» и повторить.
4. Перехватить PATCH через инструменты тестирования браузера и вернуть HTTP 500: убедиться в мгновенном обновлении и последующем откате. Ошибки не имитируются в production API.
5. Вернуть ошибку для POST комментария: текст остаётся; повторная отправка после восстановления API создаёт один комментарий.
6. Выбрать фильтры и компактную плотность; обновить страницу. Фильтры остаются в URL, плотность восстанавливается из localStorage. Проверить применение плотности на странице обзора.
